> **一句话**：diff 能证明「变了什么」，不能证明「改对了」。把前者做到可以独立复算，是验证的全部起点。

## 为什么现在必须重新谈验证

写代码、改合同、动 PPT 这三件事，在过去一年里从「人力成本」变成了「边际成本接近零」。
供给变便宜之后，稀缺的那一步不是产出，而是**确认产出确实是想要的那个产出**。

过去我们有三个隐含假设，现在三个都不成立了：

| 过去的假设 | 现在为什么失效 |
|---|---|
| 改动是人写的，人记得自己写了什么 | 改动是 Agent 写的，它记得的是自己的理解，不是文件的字节 |
| 「看一下 diff」就够了 | diff 越来越多、越来越长，逐行读不再可能 |
| 审阅者与作者在同一个工具里 | 作者是模型，审阅者是人，中间隔着一层转述 |

于是「验证」不再是流程的最后一步，而是**每一次交付的入口**。

## 验证的对象不是 Agent，是两份文件

一个常见的错误是去验证 Agent 说的话（让它自检、让它复述 diff、让它解释为什么这么改）。
这条路走不通，原因很朴素：**同一段生成逻辑既产生改动，又产生对改动的描述**，两者共享同一个盲点。

我们坚持验证的对象只有两样东西：

1. **改动前的文件**（或 git 的 base 版本）
2. **改动后的文件**（或 git 的 head 版本）

diff 是这两样东西的**确定性函数**：同一对输入，任何时间、任何地点、任何实现，都应当得到同一个答案。
只要这个性质成立，验证就和「谁做的改动」「用什么工具做的改动」解耦了。

<Callout tone="rule" title="规则 1 · 交付物里必须有 diff 本身，而不是 diff 的摘要。">
「共修改 3 处」不是证据；「第 12 行 `return` 语句里 `script` 变成了 `script, expanded`，第 5、9 行同理」才是。
只要交付物里没有可以被第三方重算的 diff，这次交付就默认未经验证。
</Callout>

## 「可验证」的四个必要条件

我们把「可验证」拆成四个可以逐条检验的条件。任何一条不成立，验证就退化成相信。

### 1. 确定性

同样的两个文件，今天算出什么，明天也应算出什么；换一台机器、换一个实现，结果不变。
这要求：比对算法不依赖运行环境（随机数、当前时间、文件顺序、locale），并且**能说清楚为什么这样判**。

diffs.work 的做法是：一个内核（Rust → WebAssembly），一条算法路径，输出只有一种形状（[portable@1](/reference/tool-contract/)）。
参考实现与内核之间存在交叉验证，任何一处判定不一致都会被测试抓住。

### 2. 可独立复算

审阅者必须能在**不被改动方控制的环境**里跑一遍同样的比对。这意味着：

- 网页里能直接比（不安装、不上传）；
- 命令行里能比（`diffs diff a b`）；
- 本地 API 能比（`POST /api/diff`，只监听 127.0.0.1）；
- Agent 调用时用的是同一个契约，而不是它自己写的一段总结。

四条路给出的是同一份 JSON。

### 3. 粒度足够细

「删了 12 行、加了 40 行」这句话几乎不含信息。要发现夹带，粒度必须细到：

- **哪一行**被改（不是「第 3 段到第 9 段整体变了」）；
- **这一行里哪几个字**被改（`buf` → `buffer`，而不是整行标红）；
- 哪一块**整体搬家**了（移动 ≠ 删除 + 新增，这是最容易藏东西的地方）；
- Office 文件里是**哪一段、哪个单元格、哪一页**。
- 代码里是**哪个函数、哪个参数、哪个 import**。

### 4. 不因为「要验证」而额外泄露

法务合同、尽调底稿、未发布代码，恰好是最需要独立复核、又最不能上传给第三方的那一类。
所以计算必须能在本地发生：浏览器里、或你自己的机器上。这不是「隐私卖点」，而是**让验证成为可能**的前提。

## 验证能做什么、不能做什么

必须明确：diff 解决的是「变了什么」，不是「该不该这么变」。

| 问题 | 谁回答 |
|---|---|
| 变了什么？ | **diff**（确定性、可复算） |
| 改了这么多，是不是想改这些？ | 人（对着需求看 diff） |
| 这么改对不对？ | 测试 + 领域判断 + 代码评审 |
| 这个改动是谁提的、什么时候算的？ | 版本控制 / 签名（规划中） |

把第一行做好，剩下的三行才有讨论的基础。把第一行交给 Agent 自述，剩下的三行都会建筑在沙子上。

## 最小可验证流程

<Callout tone="note" title="这是我们自己每天在用的流程，写下来供照抄。" />

<Doc kind="step" n="1" title="要产物，不要描述" />

让 Agent 交出改前 / 改后的文件，或一个 git 提交，而不是一段说明。文件是证据，说明是转述。

<Doc kind="step" n="2" title="在第三方位置重算一次" />

用**不属于这个 Agent 的工具**（diffs.work、CLI、CI）重算，确认增 / 删 / 改 / 移与它声称的一致。

> 下面用 `diffs <命令>` 表示 CLI。它**还没发布到 npm**，所以请先 `pnpm build:cli`，
> 再把 `diffs` 换成 `node apps/cli/lib/bin.js`。

```bash
diffs diff before.ts after.ts --json | jq '.counts'
```

<Doc kind="step" n="3" title="先看结构，再看内容" />

先看「改动分布」：改了哪几个函数、有没有整块搬家、有没有新增的 import 或依赖。
**移动与新增最容易藏东西**——一个函数被搬到另一个文件并顺手改了参数，是最典型的夹带。

<Doc kind="step" n="4" title="对改动处逐字确认" />

对每一处「改」，看的是被改动的那几个字，而不是整行。跨行重排、缩进变化、行尾空白不应当打断阅读。

<Doc kind="step" n="5" title="把这一步写进 Agent 的指令里" />

在 Agent 的 instructions / system prompt 中明确：**交付前必须附上 diff 结果**，并且不可以用摘要代替。

<Doc kind="step" n="6" title="把这一步写进团队 SOP" />

合并前由第二个人在独立工具上复核一次。这条规则的价值不在于抓错误，而在于让「没复核」这件事变得显性。

## 为什么我们把这件事开源

如果验证工具本身不可审视，那么「独立复核」只是换了一个人相信。
所以我们把**契约、SDK、站点、扩展、插件**全部开源，只把内核以二进制分发（它的接口是完全公开的）。

你可以自己实现一个内核：只要它输出 portable@1，本站就能渲染，Agent 就能消费，CI 就能比较。
验证链条的每一环都可以被替换，这才是「可验证」的最终含义。
