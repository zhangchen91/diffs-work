Markdown 与纯文本走的是和代码同一套行级比对，区别只在**怎么认定「单元」**和**怎么着色**。

## Markdown

- **单元是标题及其正文**：`## 保密义务` 到下一个同级标题之间的内容，是一个整体；
- 标题被搬走时，它下面的正文跟着一起搬——这是读者理解的「这一节移动了」，而不是「标题移了、正文删了又加」；
- 表格按行参与比对，列数变化会单独提示；
- 代码围栏里的内容按**代码**着色，但仍然按行比对。

## 纯文本

`.txt .csv .tsv .json .yml .yaml .xml .log .ini .toml` 都按纯文本处理：

- 行级比对，行内逐字；
- **没有**单元概念，因此不会报「移动」（CSV 的整行移动会被识别，但不会当成「一段内容搬家」）；
- JSON / YAML / XML 不做语法层面的「键值对齐」——这一项目前是**规划**中的；
  现在看一个键改了值，会看到该行被标出来。

<Callout tone="note" title="为什么 JSON 不做结构化比对？">
结构化比对（哪一层嵌套里的哪个键变了）需要先决定「一条数组元素的身份是什么」，
而这个问题没有通用答案：有时是 `id`，有时是下标，有时是整条内容。
在没有明确规则之前，行级比对是更诚实的答案。
</Callout>

## 日志

日志是特殊的一类：**同一份日志两次跑都不一样**（时间戳、耗时、路径、GUID）。
直接比会得到一整片差异。目前的建议：

1. 先过滤掉时间戳 / 耗时 / 随机 ID（本页面不自动做，因为过滤规则应当由用户决定）；
2. 再比过滤后的两份文本。

「按结构化字段比对日志」在规划中。

## 结果与视图

这三类共用文本族的 `hunks` 结构（见 [portable@1](/reference/portable/)）：

- 统一视图：行级 + 行内逐字；
- 并排视图：左右对齐，改动处成对显示；
- 导出 `.diff`：标准 unified diff，可以交给 `patch`。

## 常见问题

**换行符混用？** `CRLF` 与 `LF` 会被规范化为 `\n` 再比对，因此「只是换行符不同」不会产生差异。

**编码？** UTF-8（含 BOM）直接读；UTF-16 / UTF-32 带 BOM 的先转成 UTF-8 再比对；
其它编码（GBK 等）不保证正确——会出现读不懂的字符，视图会给出提示。
