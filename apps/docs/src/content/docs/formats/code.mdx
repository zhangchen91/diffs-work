代码是 diffs.work 的起点，也是最容易被「行级 diff」糊弄过去的地方。同一处改动，在行级 diff 里可能呈现成
**删 6 行 + 加 6 行**，而它其实只是把一个判断条件改了一个符号。读者要在 12 行里找出那一个字符。

## 三层判定

<Doc kind="step" n="1" title="行：哪些行变了" />

先用 Myers 求两边的**最长公共子序列**（按整行文本精确匹配）。这一步只回答「哪些行原样留了下来」。

两个文件里都没有变化的长前缀 / 长后缀不会进入计算；真正参与比对的只有中间那段。

<Doc kind="step" n="2" title="段：变了的行是一对「改」，还是「删了又加」" />

LCS 之后会出现若干**未匹配的连续段**。对每一段，不是逐行配对，而是整段规划：

- 两行如果有足够长的**公共前缀 + 公共后缀**（≥ 较长一行的 50%），就判为「同一行被改写」→ **一条改**；
- 否则就是**整行删除 + 整行新增**。

这条规则解释了所有「看起来应该算改，却被算成删加」的情况，也解释了为什么两个都以 `name:` 开头、
内容却完全不同的行不会被强行判成「改」。

<Doc kind="step" n="3" title="字：这一行里改了哪几个字" />

配对成功后，改动位置就是这一对行的**公共前缀长度**到**公共后缀起点**之间的那一段，两边各自算：

```text
旧：  end, { buffer = 0, silent = true })
新：  end, { buf    = 0, silent = true })
          └─ 删掉 "fer"，位置就在原处
```

这不是「按词猜」的结果，而是配对时用的那对前后缀本身——所以字符位置永远不会和「这是一条改」的判断相互矛盾。

<Callout tone="note" title="为什么不用「词级 diff」。">
词级 diff 会给出更漂亮的标记，但它和行配对是两套独立算法，两者很容易互相矛盾（标出来的位置对不上「这是一条改」）。
现在的做法是：**判定只有一套，标记来自判定本身**。少数情况下（把一个词整个换掉）标记会是整词，这正是该有的粒度。
</Callout>

## 「挪」不是「删了又加」

一次整块移动，在行级 diff 里天然表现为「这里删了一堆、那里加了一堆」。读者会以为逻辑被删掉了。
我们把它单独识别出来：同一份内容换了位置，**既不算删除也不算新增**，而是在两个位置之间画一条移动。

这也解释了为什么「移动」比「改」更难做对——它需要知道代码的**单元**是什么：

| 语言 | 单元 |
|---|---|
| 几乎所有语言 | 顶层声明（`fn` / `def` / `function` / `class` / `struct` / `impl` …） |
| Markdown | 标题及其正文 |
| Office | 段落 / 幻灯片 / 表格区块 |

单元在两边都完整、内容一致、位置变了 → 一次移动。单元内容变了 → 是一条改，不是移动。

## 支持的语言

扩展名决定语言，语言决定语法结构（顶层声明）与着色：

| 语言 | 扩展名 |
|---|---|
| TypeScript / TSX | `.ts .mts .cts .tsx` |
| JavaScript / JSX | `.js .mjs .cjs .jsx` |
| Python | `.py .pyi .pyw` |
| Rust | `.rs` |
| Go | `.go` |
| Java / Kotlin / Scala | `.java .kt .scala` |
| C / C++ | `.c .h .cc .cpp .cxx .hpp .hh .hxx` |
| C# | `.cs` |
| Swift | `.swift` |
| Ruby / PHP / Perl | `.rb .php .pl .pm` |
| Lua / R / Dart | `.lua .r .dart` |
| Shell | `.sh .bash` |
| SQL | `.sql` |
| HTML / CSS | `.html .htm .css .scss` |
| JSON / YAML / XML | `.json .yml .yaml .xml` 及常见 XML 方言扩展名 |
| Markdown | `.md .markdown` |

识别不出的扩展名按**纯文本**处理，不报错。

## 现在做得怎么样

我们拿 OmniDiff 官方 showcase 里的用例作为对照（其中包含本项目最早的一批手工用例），
逐行、逐字符地比对判定结果：

```bash
node scripts/omnidiff-conformance.mjs
```

<Callout tone="warn" title="诚实的状态：移动标记还不完全可信。">
拿 OmniDiff 官方 showcase 的 25 个用例逐行对照，**10 个的增删改移判定一致**。

**增 / 删 / 改 是可靠的。移动（⇅）可靠的情况**：

- 一整块相邻的行整体搬了位置，包括块中间有一行被编辑（`function f` 搬家且改了一行 → 仍是一块）；
- 一行之内某个标识符被插入的文字顶到了新列（`{A, B}` → `{A, C, B}` 里的 `B`）。

**仍不可靠的情况**：文件顶部插入或删除一行，导致下面所有行整体下移 / 上移。
这段「整体位移」仍会被标成移动，而它其实只是被顶下去了。
看到一大片连续的 ⇅ 时，请当作「这些行相对上面对齐变了」，而不是「它们搬家了」。

另外，**行内高亮的宽度**和参考不同：参考在标识符改名时会把整个名字标出来
（`EVENT_NEW_FRAME` → `SC_EVENT_NEW_FRAME`），我们只标插入的 `SC_`。
这影响的是「标得多宽」，不影响「哪一行变了」。
</Callout>

## 视图

| 视图 | 看什么 | 适合 |
|---|---|---|
| 统一 | 行级 + 行内逐字，带上下文 | 逐处确认 |
| 并排 | 左右两栏，成对对齐 | 看整体结构变化 |
| 语法 | 按语法树的列级差异 | 定位到一个 token |

三种视图读的是**同一份**结果，切换不会改变任何判定。
