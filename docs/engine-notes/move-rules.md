# 移动检测：已经确认的规则与还没解决的坑

> 这份笔记记录 `apps/engine-core/src/moves.rs` 的判定依据，以及和 OmniDiff-compatible 参考用例比对后
> 仍然不一致的地方。内核源码不入库（`.gitignore`），所以结论写在这里，避免每次重来。

## 参考用例里「移动」到底长什么样

从 `test-cases/all-ops/_reference/showcase/*.reference.json` 可以直接读出规则：

| 例子 | 参考的判定 | 说明 |
|---|---|---|
| `rust-tauri-apps-…` | `use crate::dpi::{PhysicalPosition, ` **`PhysicalSize`** `};` | 行内位移：`PhysicalSize` 在 before 是第 35 列，after 变成第 49 列，就是一次 move |
| `rust-add-if` | `if number % 2 == 0 { … }` 整块 | 整行滑动：块在 after 整体下移 |
| `typescript-add-type-annotations` | `function addUser(…) { … }` 整块 | 插入 `interface` 后整块下移，但 before 侧首行被标为 move |
| `c-genymobile-scrcpy-rename-defines` | **不是** move | `EVENT_NEW_FRAME` → `SC_EVENT_NEW_FRAME` 是改名，标记整词但要算 update |

结论：参考实现里 move 是**字符区间级**的概念（`[row, col] → [row, col]`），不是行级。

## 我们现在的实现（`src/moves.rs`）

两条**精确**规则，都能从文本本身复算：

1. **整行滑动**：行 diff 匹配到、但行号不同的连续行 → 一次 move。
   但若它上面那行也以同样偏移滑了（说明是上面插入导致的下移），则不算。
   判据用「该 run 的上面是否有 delete」。
2. **行内位移**：一行被改写，但改写后的另一半是**另一行原样文本挪到了新列**，且这个片段：
   - 从**词字符**开始（`PhysicalSize` ✓，` 18;` ✗）；
   - 长度 ≥ 2（`>=` 这种单个标点滑动算改，不算移）；
   - 不是「同一个标识符换了拼法」（`EVENT_NEW_FRAME` → `SC_EVENT_NEW_FRAME`）。

另外：move 会**认领它两侧的确切行号**（含行 diff 记成 add/delete 的边缘行），
被认领的行不再以 insert/delete/update 重复出现。行内位移还会抑制该行自身的 update。

## 还没解决的（按影响排序）

1. **整行滑动的 run 边界**。`examples/code/hours-v2.md` 里 "Where the numbers live" 一节
   从第 11–13 行移到第 17–19 行，但中间的 `## Rules of thumb` 也动了，导致 run 检测漏判。
   需要重写 `row_runs` 的 run 切分：按「同偏移的最长连续段」切，而不是按 pair 相邻。

2. **删了又插（同一段文本）**。参考会把这类判成 move，我们目前做不到——
   `deleted_runs()` 写了一版但不够准（会把「相邻插入」误判成整节移动），已 `if false` 关闭。

3. **单行内改一个词**，参考判 delete+insert，我们判 update（`kotlin`、`java` 两个用例）。
   试过按「改写片段词数」区分，会破坏「改一个数值算改」这条核心契约，已回滚。

## 第 7 轮：想把两个内核测试修掉，结论是「不能只修一个」

目标是把 `classify.test.mjs` 里剩下的两个红灯修掉：

1. `## Known gaps` → `## Open questions` 应该算一次「改」
2. `legacyTax(...)` 换成 `taxIncluded(...)` 不该把两个函数的 body 配成一条「改」

### 做出来的

- 在 `shared_affix` 里加「同级标题可以配对」→ 测试 1 通过，内核测试到了 **99/99**；
- 在 `plan_gap` 里加「两个不同声明不配对，但改名可以」→ 测试 2 也通过；
- 两条一起上：**99/99 内核测试全绿**。

### 代价

但 `hours.md` 样例掉了：`## Where the numbers live` 和 `## Rules of thumb` 都是二级标题，
新增的标题规则把**两节不同的内容配成了一条「改」**，于是那一次真正的编辑消失了
（`u=1` 变成 `u=0`）。参考用例一致数 10 → 9。

试过三种收窄方式，都失败：

| 收窄方式 | 结果 |
|---|---|
| 要求两标题共享至少一个词 | `Known gaps` / `Open questions` 一个词都不共享 → 测试 1 重新变红 |
| 只在「gap 里只有一个标题」时允许 | hours 里 `## Where` 移动后正好形成一个单标题 gap → 仍然误配 |
| 只加标题规则、不加声明规则 | 样例仍然掉（误配就发生在标题规则上） |

### 为什么放弃

判断「两个标题是同一个位置被改写」还是「两节不同内容换了位置」，需要**文档级信息**
（这一节的正文有没有跟着走），而不是两行文本能决定的。用行级规则硬判，一定会在
「同名标题」和「移动的节」之间二选一，而这两个场景在真实文档里都会出现。

### 现状

保持了**内核测试 97/99、样例 9/9、参考一致 10/25**这一版二进制。
两个测试仍然红，它们记录的是一个真实的、已知的能力边界，而不是随手留下的噪音。
要真正修掉，需要让内核看见文档结构（标题 + 正文归属），这和移动检测缺语法树是同一个根因。


## 第 8 轮：拿到了节区间，但问题不在那里

上一轮认定「判断标题改写 vs 整节移动需要文档级信息」。这一轮发现内核**本来就有**这个信息：
`astdiff::top_level_units` 会给每个标题算出 `(起始行, 结束行)`。

于是新增了 `linediff::SectionIndex`（每个标题管辖的行范围，到下一个同级或更高级标题为止），
把两份文件的节区间传进 `line_diff_with_sections`，并让 `plan_gap` 用
「两边的标题都**没有**正文」作为配对前提。

### 结果

- `SectionIndex` 算得是对的（hours-v1 第 11 行 → 节 11..14，正文 3 行；第 15 行 → 节 15..19，正文 4 行）；
- `line_diff` 的输出也是对的（整个文件只有 1 处 update，就是第 3 行那句被扩写的段落）；
- **但 `sem_diff` 最终结果里 update 变成 0。**

也就是说：行级判定是对的，**丢失发生在 `semdiff::render` 的「一行只显示一次」逻辑里** ——
移动块把它附近的一行当成了自己的一部分，于是那一行的 `upd-del/upd-ins` 被跳过了。

### 结论

问题不在「缺文档结构」，而在**移动块的边界算得太宽**（和第 2 条同源）。
补结构信息是必要的，但不充分；先把 move 的边界收准，这条才可能真正修好。

### 现状

仍然是 **97/99 内核测试、9/9 样例、10/25 参考一致**。这一轮的代码没有提交（比基线差），
但 `SectionIndex` 的设计留在这里，等 move 边界修好之后可以直接复用。


## 第 8 轮补充：一个真实的残留 bug（已定位，未安全修复）

`row_runs` 里有一段残留代码，会在算出块的 `old_rows` / `new_rows` 之后**再多塞一行**：

```rust
if old_rows.last() < a.len() { old_rows.push(last + 1); }        // 多认领下一行
if shift < 0 && old_rows[0] > 1 { old_rows.insert(0, first - 1); }
if new_rows.last() < b.len() { new_rows.push(last + 1); }
```

它是早期为了「把块边缘那行也算进移动」而写的。后果是：**块旁边的一行被移动吞掉**，
于是那一行自己的 `upd-del/upd-ins` 在 `render` 的「一行只显示一次」里被跳过 ——
这正是 `hours.md` 第 3 行那句话编辑消失的机制。

删掉这三段后：参考一致数从 9 回到 10，但内核测试从 97 掉到 96。
说明这几行当初也顺手掩盖了别的问题。**需要连它掩盖的那个问题一起解，才能一起删。**

记录在这里，避免下次再把它当成无关紧要的代码。


## 第 9 轮：那三行继续留着，原因已经清楚

删掉「多认领一行」的三行后，`hours.md` 的真实编辑回来了（参考一致 9 → 10），
但 `移: identical block` 这个测试立刻变红：

```
a X1 X2 X3 b  →  a b X1 X2 X3
```

`b` 从第 5 行到了第 2 行。行 diff 把它记成「第 2 行插入 b、第 5 行删除 b」，
当它**不是**任何移动块的一部分时，就会出现 `+1/-1`——而这份数据里它确实只是"被搬家带走的位置"。

### 试过的三条路，都不通

| 做法 | 结果 |
|---|---|
| `render` 里把「落在移动块区间内」的行也算作被认领 | 会吞掉紧挨移动块的真实编辑（`hours.md` 那句又消失）——这正是原来的 bug |
| 让 `deleted_runs` 认出 `b` 这类行 | 认出来了，但它和 `X1..X3` 的移动块**相邻**，两个块被合并成一个，`b` 仍不在里面 |
| 兼容两者（移动块 + 边缘行） | 需要区分「边缘行是被搬走的」还是「边缘行是真的增删」，而这两者在行级数据里长得一模一样 |

### 结论（重要）

这三行不是随手留下的垃圾，它们是**对「移动块边缘语义」的一个错误近似**。
正确做法需要知道「这一行和这个块在 after 里是连续的吗」——也就是块的边界语义，
而不是在认领集合里补行。

在拿到块的精确边界之前，保留它们是**两害相权取其轻**：让一个测试红，而不是让
`hours.md` 那种真实编辑在结果里消失。用户看不到测试，但看得到被吞掉的编辑。

### 现状

**97/99 内核测试、9/9 样例、10/25 参考一致**。不再在这条线上做无把握的改动。


## 第 10 轮：按「块边界」重写，还是不行

这一轮不再打补丁，而是把 `row_runs` 整体按块边界重写：

- 块 = 两侧都连续、共用一个 offset 的一段匹配行；
- 判据看**边界**：进入这个块的那一侧 offset 是否和块本身不同；
- 两侧都被不同 offset 夹住 → 属于编辑窗口，不是搬家。

结果：参考一致仍是 10，内核测试 96（比基线少 1）。**没有改善。**

接着单独攻「移动块旁边的行」（`pure move` 里 `b` 从第 5 行到第 2 行那个 +1/-1）：

| 尝试 | 结果 |
|---|---|
| 把「落点相同」的边缘行并进块（向下/向上生长） | `b` 的偏移是 −3，块的偏移是 +1，够不着 |
| 让 `deleted_runs` 单独成块，不与相邻匹配块合并 | `b` 能被识别成独立块了 |
| 但块的范围算出来是 `[2,3]`，把 `X1..X3` 挤掉了 | 需要「块是按 after 侧顺序排列还是按 before 侧」的额外约束 |

### 真正的结论

`b` 这一行揭示的是：**一次改动里可以同时存在两个方向相反的移动**
（`X1..X3` 向下 1 行，`b` 向上 3 行），而它们共享同一段 after 区间。
用「一个 offset 描述一个块」的模型，这类情况必然算错。

参考实现能对，是因为它按**字符区间**同时记录两侧位置（`[行,列] → [行,列]`），
一个块可以有自己的 from/to 而不依赖全局 offset。

**这已经超出「调参」的范围，是需要换数据结构的事。** 在行级 + 单 offset 的模型里，
`pure move` 这个最简单的情形都做不对。

### 现状

**97/99 内核测试、9/9 样例、10/25 参考一致** —— 回到并保持在第 4 轮的稳定版本。
第 5–10 轮共 6 轮内核尝试，净收益为零，全部回滚；所有失败原因都在本文档里。


## 第 14 轮：Excel 的实体级比对，改对了但没能合并

目标是用户自己给的验收契约 `test-cases/all-ops/expected.json`（7 组、每组要求 1 增 1 删 1 改 1 移）。

### 现状核对（大部分是对的）

| 配对 | 结果 |
|---|---|
| ts / rust / md | ✅ 增删改全部命中（`roundHalfUp` 增、`legacyRound` 删、`applyTax` 改、`parsePrice` 移） |
| word / ppt | ✅ 2 增 2 删，实体正确 |
| pdf | ⚠️ 无差异（PDF 走独立引擎，CLI 不做对象级比对） |
| **excel** | ❌ **按单元格坐标配对，行移动/删除被读成一串「改」** |

Excel 的问题：before 第 2..6 行是 A-001..A-005，after 是 A-002/A-003/A-004/**A-001**/A-006。
内核按 `A6` 对 `A6` 比，于是得到 `A-005 → A-006`、`轴承 → 弹簧`、`50 → 60` 三个「改」，
**A-005 的删除和 A-006 的新增都消失了**，预期里的「移」（A-001）也不可见。

### 修法（已在 `sheet.rs` 里做出来，效果对）

在「文本完全相同的行按顺序重映射」之后，再加一层**按首列（编号列）匹配**：

- 编号相同 → 是同一行，比较其余列（这样 A-003 的 30→35 被正确定位到 C4）；
- 编号不同 → **不是同一行**，老行剩下的单元格记为删除、新行记为新增。

实测结果与契约完全一致：

```
totals {"added":4,"removed":4,"modified":1,...}
del A6 "A-005" / del B6 轴承 / ...
add A6 "A-006" / add B6 弹簧 / ...
mod C4 "30" -> "35"
```

### 为什么没合并

`sheet.rs` 的修复本身是对的（`core-xlsx` 11/11 通过），但把源码快照重新编出来后，
**内核测试和 `hours.md` 样例都退了一步**——原因是 `semdiff.rs` / `linediff.rs` 里还残留着
第 8、10 轮未清理的实验代码（`SectionIndex`、`column_move` 抑制、`row_runs` 重写），
它们和发布二进制不一致。修一处、另一处就掉。

这暴露了一个更根本的工程问题：**内核源码不入库，所以没有「回到已知良好状态」的办法**。
每一轮实验都只能靠回滚二进制，源码则越滚越乱。

### 建议（下一步最该做的一件事）

把 `apps/engine-core/` 纳入版本控制（私有仓库或 git submodule），并给它一个
`git revert` 可用的历史。在那之前，继续改内核的期望收益是负的——
第 5、7、8、10、14 轮都是这个模式。

本轮不改发布二进制：**97/99 内核、9/9 样例、xlsx 11/11**。


## 第 15–16 轮：先修工具，再修功能

第 14 轮卡住的原因不是「移动检测难」，而是**内核源码没有版本控制**：
`apps/engine-core/` 在 `.gitignore` 里，改坏了只能回滚二进制，源码于是越滚越脏，
到了「修 A 破 B」无法收敛的地步。

### 现在有了

`apps/engine-core/` 有自己的 git 仓库（公开仓库仍然不含源码，那是刻意的）。
`git ls-files` 能看到 15 个源文件。这意味着：

- 每个改动都可以 `git revert`；
- 源码和发布二进制可以对齐（本轮已对齐：`samples 9/9`、`kernel 98/99` 从源码重新编译可得）。

**用法**：改内核前后都在 `apps/engine-core` 里 commit，然后
`node scripts/build-rules-core.mjs` → `pnpm test:rules` → `node --test apps/website/test/samples.test.mjs`。
倒退就 `git checkout -- src/` 重编，一步回到已知良好状态（本轮实测有效）。

### 用这个新条件做成的事

- 清掉两个实验残留（`column_move` 抑制、SectionIndex 测试），源码回到与发布一致；
- **Excel 按实体比对**：行按首列编号匹配，编号不同 = 一行走了 + 一行来了。
  实测 `+0/-4/~8` → `+4/-4/~1`，与 `expected.json` 完全一致；
- CLI 对「没比较」的文件（PDF）明确输出 `NOT COMPARED`，不再用 0/0 假装比过了。

### 又试过、又失败的（本轮）

- 给纯移动用例补第二个块（`b` 从第 5 行到第 2 行）：`deleted_runs` 认得出，
  但合并阶段它会和相邻块粘在一起；改成「同 offset 才合并」后 `b` 又走不出过滤。
  样例从 9/9 掉到 8/9，**已用 git 干净回滚**。
- 结论不变：纯移动用例需要「一个块可以有自己两个方向的位置」，单 offset 模型表达不了。

### 现状

`kernel 98/99`、`samples 9/9`、`xlsx 12/12`、`cli 16/16`、`website 32/32`、参考一致 10/25。


## 第 17 轮：双向移动还是没做成，但拿掉了一个前置障碍

目标：让「一个块可以有两个方向的位置」，从而修好纯移动用例
（`a X1 X2 X3 b` → `a b X1 X2 X3` 里 `X1..X3` 向下 1 行、`b` 向上 3 行）。

### 做成的一件（已提交）

**移动块改为从 before 侧描述。** 之前移动 hunk 是遍历行列表、只取「匹配行」，
而一个「删了又插」的块根本没有匹配行——它的行在行 diff 里是彻底的删 + 彻底的插，
于是这类块被静默丢掉，读者看到同一个变更出现两次（一次当删除、一次当新增）。

现在按块自己的 before 范围生成，不依赖行 diff 怎么分类那些行。
内核 98/99、样例 9/9 不变——这是地基，不是功能。

### 没做成的（已 git 回滚）

试着放行单行块（`b` 这种单标识符），结果连带放进了散文里的词：
`hours.md` 第 3 行被改写后，共享的单词 `and` 被当成了一个「移动」。
连环加了三个护栏（要求是标识符 / 要求非零位移 / 要求片段不超半行）都没能同时满足
「`b` 要进」和「`and` 要出」——**样例从 9/9 掉到 8/9，整批回滚**。

### 结论（第 3 次确认）

`row_column_moves`（行内片段位移）和 `row_runs`（整行滑动）用的是**同一个 Move 结构**，
但前者需要的是「片段在行内的两个列位置」，后者需要的是「块在文件中的两个行位置」。
把它们塞进同一个结构，判据就会互相污染——这正是 `and` 能混进来的原因。

**下一步应该是拆成两种移动类型**（`Move::Block` 和 `Move::Within`），
各自带自己需要的位置信息，而不是继续在 `Move` 上加布尔开关。
现在有 git 兜底，这种重构可以分步提交、随时回退。

### 现状

`kernel 98/99`、`samples 9/9`、`xlsx 12/12`、`cli 16/16`、`website 32/32`，参考一致 10/25。


## 第 18 轮：按上一轮的诊断做了类型拆分

上一轮的结论是「两种移动共用一个结构，判据互相污染」。这轮拆了：

`Move` 的 `from_col` / `to_col` 改成 `Option<usize>`，并加 `is_within()`：
- **块移动**：只有行位置，没有列位置；
- **片段移动**：有列位置。

行为不变（98/99、9/9、12/12），这是重构该有的样子——它买的是「下一个改动有地方站」。

### 拆分带来的两处真改进

1. **单行块必须是名字或有结构的行。** 散文里 `and` 在两版之间都有，
   之前被报成「移动」。这条规则只作用于块，片段路径按列判断，不会看到它。
   → `hours.md` 的假移动**消失了**。
2. **块按位移分组**。之前只按行排序，向下走的块和向上走的行在列表里相邻，
   分组时被合并成一个——第二处移动就此消失。

### 还没修好的

纯移动用例（`a X1 X2 X3 b` → `a b X1 X2 X3`）里，`b` 仍会额外产生 +1/-1。
追到 `find()` 里 `b` 已经被收进 `moved`、也进了块循环，但最终没出现在结果里。
**这部分还没查完**，下一轮继续。

### 现状

`kernel 98/99`、`samples 9/9`、`xlsx 12/12`、`cli 16/16`、`website 32/32`，参考一致 10/25。


## 第 19 轮：内核测试 **99/99 全绿**（第一次）

跟第 18 轮留下的线走到底，找到三个缺陷，每个都是「同一个判断写了两遍」：

1. **单行块的长度门槛出现了两次。** 前面已经按「必须是标识符或有结构的行」判断过，
   后面又按 `len < 3` 判一次——`b` 这种短名字在前面通过了、在后面被丢掉。
2. **块内被编辑的行被当成了块外。** 一个函数整体搬家、但里面有一行改了内容，
   那一行没有配对，块就被切成三块（`function f() {` / `}` 各成一块）。
   现在允许块内留一个「洞」（偏移一致、洞≤3），洞里的行照常作为「改」报告。
3. **下游又过滤了一次。** `semdiff` 里还有个 `len < 4` 的过滤，把检测器刚决定保留的
   短移动又扔掉。

顺带把片段规则收紧到「整条共享尾巴不能占半行以上、且不含空格」，
`hours.md` 里那个假的 `and` 移动彻底消失。

| 指标 | 之前 | 现在 |
|---|---|---|
| 内核测试 | 98 / 99 | **99 / 99** |
| 样例测试 | 9 / 9 | 9 / 9 |

### 仍然差的

严格对照（含标记列）3/25——差的是**行内标记的宽度**（参考把改名后的整个标识符标成变化，
我们只标差异部分），不是「增删改移」的判定。这个差距是独立的，可以单独做。

**教训（值得记住）**：这一轮三个缺陷的共同形态是「同一个规则在两个地方各写了一遍，
两处逐渐不一致」。以后加规则应当只加一处。


## 第 20 轮：标记宽度试了两次，两次都是净负面

剩下唯一的参考差距是**行内标记的宽度**：`#define EVENT_NEW_FRAME` → `#define SC_EVENT_NEW_FRAME` 时，
参考把整个标识符标成变化，我们只标插入的 `SC_`。

### 试了什么

在 `inline_segments` 里加「两端都落在同一个标识符内部 → 把这个标识符整个标出来」。

### 结果（两次都回滚）

| 版本 | 内核 | 样例 | 标记命中 |
|---|---|---|---|
| 基线 | 99 | 9/9 | **19/38** |
| 不加限定的版本 | **92** | **6/9** | — |
| 限定为「代码形状的行」 | 98 | 9/9 | **18/38** |

第一次把文档和表格的标记也弄宽了（`30 日` → `45 日` 被判成改名），第二次虽然保住了样例，
**标记命中反而从 19 掉到 18** —— 说明这个「改名整词标记」在其他用例上换错了方向。

另外第一次的实现有个越界 bug，**会让 wasm 崩溃**（`RuntimeError: unreachable`），
靠样例测试才发现。这条值得记住：**标记类的改动必须跑样例，不能只看单测。**

### 结论

「参考把整词标出」这条规则**不能当作通用规则**照搬。它在 `#define` 上对，
在 `function old()` 上就错（那里 `(` 让中间段不再是标识符内部），
在表格单元格上更错（单元格里的值不是名字）。

**做这件事需要「这一行是什么」的判断**（宏定义 / 函数签名 / 单元格 / 散文），
而 `inline_segments` 只看两个字符串——它没有这个信息。

### 现状（与第 19 轮相同，已回到这个状态）

`kernel 99/99`、`samples 9/9`、`xlsx 12/12`、逐行一致 **10/25**、严格一致 3/25（差的是标记宽度）。
